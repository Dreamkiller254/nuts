# Nuts Paradise SEO Master Plan — Closing Sprint

**Job name:** Nuts Paradise Search Dominance — Production SEO Master Plan  
**Status:** Ready for execution  
**Branch:** `mockone`  
**Execution owner:** ChatGPT  
**Primary domain:** `https://nutsparadise.co.za`  
**Scope:** Maximize technical SEO, search intent coverage, entity clarity, crawlability, search appearance, internal authority and conversion quality using only verified content already available in the repository.

---

## 1. Execution mode — how this will actually be done

This is **not** an eight-phase implementation project.

The closing SEO work will be executed in three practical waves:

### WAVE A — REPO SEO ONE-SHOT

ChatGPT will execute every SEO improvement that can be completed from the current repository and verified public information in **one aggressive implementation pass** on `mockone`.

This includes:

- search-intent mapping for every existing public route;
- title and meta-description refinement;
- canonical and indexability hardening;
- semantic heading review;
- JSON-LD entity/schema implementation;
- breadcrumb structured data;
- Organization/WebSite/WebPage graph;
- ContactPage, AboutPage and CollectionPage typing where appropriate;
- sitemap improvement;
- robots and crawler-control review;
- duplicate URL protection;
- internal-link architecture;
- image SEO and delivery review;
- Core Web Vitals/performance cleanup that can be done in code;
- accessibility/search-rendering checks;
- SEO regression tests;
- removal of obsolete SEO-unfriendly legacy code or metadata;
- production-domain consistency checks.

**No placeholders, dummy copy, “coming soon” sections, empty content hubs or speculative landing pages may be introduced.**

### WAVE B — PRODUCTION CUTOVER CHECK

Once the final build is deployed to `nutsparadise.co.za`, perform one launch verification pass:

- HTTPS and preferred-host redirects;
- production `APP_URL`;
- live canonicals;
- live Open Graph URLs;
- sitemap URLs;
- robots.txt;
- public crawlability;
- status-code crawl;
- Rich Results validation;
- Lighthouse/PageSpeed on the actual production network;
- Search Console/Bing verification and sitemap submission where account access is available.

This is separate from Wave A because live DNS, TLS, crawler access and real production response behavior cannot be validated purely from the repository.

### WAVE C — SEARCH GROWTH

After indexing begins, use real search data rather than guesses:

- Search Console queries and impressions;
- CTR opportunities;
- pages Google is choosing for queries;
- indexing/canonical issues;
- actual Core Web Vitals field data;
- earned links and brand mentions;
- competitor movements;
- buyer questions that emerge from real enquiries.

Authority building and ongoing content are not part of the closing code sprint because they depend on time, external websites and real market evidence.

**Bottom line:** the website SEO implementation itself is a one-shot. Search growth afterward is iterative by nature.

## 5. Technical SEO — zero ambiguity

### Preferred domain

Production must have exactly one canonical host.

Target:

`https://nutsparadise.co.za`

At launch:

- HTTP → HTTPS permanently;
- alternate hostnames → preferred hostname permanently;
- no redirect chains;
- all canonicals use the preferred hostname;
- all Open Graph URLs use the preferred hostname;
- sitemap uses the preferred hostname;
- JSON-LD uses the preferred hostname.

### Canonicals

Every indexable public page must:

- return 200;
- output one self-referencing canonical;
- use the correct production hostname;
- avoid query-string duplicate canonicals;
- avoid case/trailing-slash duplicates.

The legacy `/quality` route remains a permanent redirect to `/quality-certification`.

### Indexability

**Index:**

- home;
- about;
- products;
- macadamias;
- cashews;
- processing;
- quality/certification;
- traceability;
- buyers;
- export markets;
- contact.

**Noindex or non-indexable by design:**

- 404 pages;
- authenticated dashboard/settings/admin surfaces;
- login/register/reset routes where applicable.

Privacy/Terms require an explicit decision during execution. If the current production wording is retained but not formally approved for search visibility, use `noindex,follow`; do not show placeholder language.

### JavaScript and Livewire

The premium `wire:navigate` experience must remain.

SEO requirements:

- every navigation item remains a real HTML `<a href>`;
- every public URL renders complete useful HTML on direct request;
- no content requires JavaScript to exist in the initial server response;
- the persistent header cannot cause stale canonical/title metadata;
- browser navigation must not create duplicate history URLs;
- the custom skeleton remains visual only and does not become indexable pseudo-content.

### Status codes

- Valid page: 200.
- Permanent moved alias: 301/308 as appropriate.
- Unknown page: true 404.
- Do not redirect every missing URL to the homepage.
- Do not create soft 404s.

## 7. Structured data — conservative, connected and real

JSON-LD should be server-rendered in the Blade `<head>` or immediately associated with the rendered page, using a connected `@graph` and stable `@id` values.

### Required core graph

#### `Organization`

Use verified fields only:

- `@id`: production-domain organization anchor;
- name: Nuts Paradise;
- URL;
- logo;
- public email;
- public telephone;
- verified addresses in Mbombela and Johannesburg represented accurately;
- description consistent with the visible site.

Do **not** manufacture founders, founding dates, social profiles, VAT/company IDs, opening hours or service areas.

#### `WebSite`

- name: Nuts Paradise;
- URL;
- publisher → Organization `@id`.

Do not add `SearchAction` unless the site genuinely has site search.

#### `WebPage`

Every public page should identify:

- URL;
- name;
- description;
- `isPartOf` WebSite;
- `about`/publisher Organization where appropriate;
- primary image where appropriate.

### Page-specific types

Use when accurate:

- `/about` → `AboutPage`;
- `/contact` → `ContactPage`;
- `/products` → `CollectionPage`;
- inner pages → `WebPage` unless a more accurate supported type is genuinely justified.

### Breadcrumb schema

Every inner page receives `BreadcrumbList` matching the visible breadcrumb hierarchy.

Examples:

- Home → Products → Macadamias;
- Home → Products → Cashews;
- Home → Quality & Certification.

### What we will NOT add in this closing sprint

#### Product rich-result schema

Do not force `Product` rich-result markup while approved product identifiers, grades, offers, pricing/availability and richer product data are unavailable.

The page can rank as an excellent commercial product-information page without fabricated Product markup.

#### FAQ rich-result chasing

Real buyer FAQs may be useful later, but no FAQ section will be created merely to add `FAQPage` markup.

#### Reviews/ratings

No review or aggregate-rating schema without real attributable reviews.

### Validation

All structured data must:

- match visible page content;
- validate syntactically;
- avoid critical Rich Results errors where a Google-supported rich-result type is used;
- contain no hidden claims.

## 10. Image SEO and synthetic-image rule

Existing approved/repository imagery is preferred.

Image optimization should include:

- WebP/AVIF where useful;
- responsive source sizes;
- explicit width/height;
- lazy loading below the fold;
- `fetchpriority="high"` only for the true LCP image;
- descriptive filenames where changing them provides a real benefit without breaking references;
- accurate alt text describing what is actually visible;
- no keyword-stuffed alt text;
- no duplicate giant source assets loaded unnecessarily.

### If a new image is genuinely needed

ChatGPT may generate a **photorealistic editorial/product visual** only when it materially improves a page and existing imagery cannot fill the role.

Generated imagery must:

- look photographic and production-grade;
- match the deep-green/premium agricultural visual system;
- depict only generic macadamia/cashew/origin/export concepts supported by the site;
- never pretend to show the actual Nuts Paradise factory, staff, equipment, certificate, farm, warehouse or customer;
- never fabricate packaging, labels, grades or logistics partners;
- never be used as evidence of a factual business claim.

If provenance could be misunderstood, frame it as illustrative imagery rather than documentary facility evidence.

No image will be generated just to fill space.

## 17. Sitemap, robots and discovery

### Sitemap

The sitemap must contain only:

- canonical URLs;
- indexable URLs;
- 200-response URLs.

Do not manufacture `lastmod` dates.

If genuine route-level modification dates can be derived reliably from maintained content metadata, include them. Otherwise omit `lastmod` rather than sending false freshness signals.

### robots.txt

Must:

- allow public assets required for rendering;
- reference the production sitemap;
- avoid accidentally exposing a staging sitemap;
- keep private/admin routes out of crawler paths where appropriate.

Robots rules are not a substitute for authentication or `noindex` decisions.
